# Plan: Billing Reliability Wave (#10 → #4+#6 → #5 → #9)

Approved 2026-07-17. Order: **#10 (this PR, merged first) → #4+#6 → #5(variant A) → #9**.
Each phase: TDD (RED→GREEN), reviewer-gated, its own PR, green integration-ci + go-ci + infra-ci.
Out of scope: orchestrator (#3/#7/#8), VPS apply, #11, #15.

## Phase 0 — #10: PostgreSQL integration CI  ✅ (this PR)

- One `postgres:16` service, **two databases** (`billing_test`, `cp_test`) — billing and
  control-plane share table/migration names, so a shared DB would collide.
- `make test-integration`: billing `go test -count=1 ./...` (DATABASE_URL ← BILLING_DATABASE_URL)
  + control-plane `go test -count=1 -tags integration ./...` (TEST_DATABASE_URL). Billing schema
  applied out of band; control-plane runs `migrate.Up` in-test.
- **Skip-guard:** `REQUIRE_INTEGRATION_DB=true` (only in the integration job) turns a missing DB
  into `t.Fatal` — a silently-skipped suite can never pass green. Not `CI=true` (GitHub sets that
  in plain go-ci too).
- Surfaced + fixed two test-only fallouts from the register-hardening (invisible before, no
  integration CI): control-plane integration seeded an active node via `Register` → store seam;
  billing integration tests were not isolated (global `LeaseStuckSettlements`) → per-test TRUNCATE.
- Evidence: `TestPostgres_LeaseConcurrentExclusive` runs (PASS, not skipped); positive run
  deterministic ×2; empty DSN + REQUIRE_INTEGRATION_DB → red. go-ci stays green (integration
  self-skips / not compiled without the tag). No production schema change.

## Phase 1 — #4 + #6: atomic create+link AND cross-instance serialization

- **(a)** Transactional control-plane subscription create+link: `SELECT user FOR UPDATE` → if
  `subscription_id` set → typed conflict; else `INSERT subscription` + `UPDATE user` in one tx.
  Closes double-create (#4) and the orphan window (#6). Wire unchanged; memory mirrors.
- **(b)** Cross-instance serialization of the whole Activate path (two DISTINCT invoices for the
  same user must yield one subscription with **two** periods, none lost). Postgres advisory lock
  in the billing DB keyed per anon_user, held across GetUser → create/reuse → GetSchedule →
  SetSubscriptionPeriod → UpsertSchedule.
- Acceptance: two distinct paid invoices, same new user, concurrent → one subscription, expiry
  = start + 2×duration; replay of the same invoice adds zero (ClaimSettlement); no orphan; memory
  mirrors. Unique index only as defense-in-depth after auditing existing data.

## Phase 2 — #5 (variant A): confirmed-before-deadline+grace

- Accept any sufficient payment confirmed before the **effective deadline** = `ExpiresAt +
  SETTLEMENT_GRACE` **for on-chain only**; other gateways expire at `ExpiresAt`. NOT proof of
  broadcast time — named accordingly.
- Sweep-safety with multiple pollers: durable claim so `ExpireOverdue` cannot expire an invoice
  within grace or one taken for chain-check/settlement. Test includes concurrent poll vs sweep at
  the grace boundary.

## Phase 3 — #9: recovery observability (not optional)

- `Reconcile` returns a structured report (recovered/failed counts + failed invoice IDs, no PII)
  + an aggregate error; poller continues the rest but returns/logs the final error with IDs.
- Acceptance: unrecoverable invoice → report.failed + non-empty aggregate error + log; batch
  [broken, good] → good recovered, broken reported; one broken invoice never blocks the others.

## Locked requirements for future phases
- **Advisory lock (Phase 1):** must be acquired and held on ONE dedicated Postgres session
  (a single connection/tx, `pg_advisory_xact_lock` or a checked-out conn) and **guaranteed
  released** on every path (commit, error, panic) — never leaked across pooled connections.
- **Poll-claim (Phase 2):** must be a **lease with expiry + recovery** (like the settlements
  reconcile lease), NOT a permanent boolean claim — a crashed poller must not wedge an invoice
  forever.
