# CasperVPN — Delivery: многоканальная доставка подписки (threat-model)

Подсистема `services/delivery/`. Источник истины по архитектуре —
[`../../../architecture.md`](../../../architecture.md) §«Децентрализованная доставка
конфигов», требования — [`../../../CLAUDE.md`](../../../CLAUDE.md) [АНТИ-БЛОК].

## Проблема и модель угроз

Блокируют не VPN, а **точку раздачи** подписки. Противник (ТСПУ/РКН-класс) умеет:
SNI-фильтрацию, активный пробинг, энтропийный анализ, блокировку доменов/IP пачками,
DNS-подмену, а также **подмену артефакта** (отдать клиенту «свой» список нод —
honeypot). Значит недостаточно «спрятать» точку раздачи — раздаваемое надо ещё и
**аутентифицировать**.

Ответ delivery: один и тот же **подписанный** артефакт раздаётся через ≥4 канала
**разной природы** (мессенджер / DNS / git-raw / стего). Отказ или захват любого
одного канала не рвёт доступ. Список каналов и точек — **динамический**, из конфига.

## Ядро: артефакт, подпись, шифр указателя

- **Артефакт** (`internal/artifact`) — медиа-независимый конверт с детерминированной
  сериализацией. `Kind`:
  - `directory` — **динамический список** точек входа/зеркал/бот-хэндлов. Перед
    выкладкой в публичный канал он **зашифрован** (sealed) — это «зашифрованный
    указатель». Секретов юзера не содержит.
  - `subscription` — персональная выдача (base64/sing-box/Clash), только по
    **аутентифицированным** путям (бот после опознания юзера, `/d/{ch}/{token}`).
- **Подпись Ed25519** (`internal/sign`) — подписывается канонический байт-образ
  артефакта. Verifier — это **keyring** (`KeyID → pubkey`): держит текущий и прошлый
  ключ, ротация ключа не рвёт доставку. Клиент **обязан** проверять подпись; канал,
  вернувший непроверяемые байты, для resolver’а = «пусто», он идёт дальше.
- **Шифр указателя AES-256-GCM** (`internal/seal`) — только directory-указатель.
  Свежий nonce на каждый seal → одинаковый указатель даёт разный шифротекст (нет
  паттерна для фингерпринта). Ключ — из конфига (`DELIVERY_SEAL_KEY`), не в коде.

Поток: `directory JSON → seal → artifact(directory) → sign → wire` (в канал).
Разбор у клиента: `Open(проверка подписи) → seal.Open(дешифр) → directory`.
**Порядок жёсткий: сначала проверяем подпись, потом дешифруем.**

Инвариант: в открытые каналы (DNS/DoH/git-raw/стего) уходит **только**
sealed(directory). Персональные `uuid`/`reality_short_id`/токены — никогда.

## Каналы и их threat-model

Общий контракт `channel.Channel`: `Publish` / `Fetch` / `Healthy`. `Resolver`
перебирает каналы по приоритету до первого блоба, **прошедшего проверку подписи**
(failover). `Publisher.Broadcast` кладёт свежий directory во все каналы разом.

### 1. Telegram-бот (+ Max-совместимый) — `internal/channel/telegram`

- **Роль:** по команде (`/get`) выдаёт актуальную subscription-ссылку и deep-link
  Happ; как generic-канал умеет отдавать подписанный directory-блоб.
- **Max:** та же логика бота за интерфейсом `BotAPI`, два адаптера (`TelegramAPI`,
  `MaxAPI`) → мессенджер-канал сам по себе избыточен по двум сетям.
- **Аутентификация:** subscription-ссылка выдаётся в приватный чат опознанному
  `TelegramID` — это легитимный аутентифицированный путь для секрета.
- **Rate-limit / антиспам:** token-bucket на юзера + глобально; дубль одинаковой
  команды в cooldown-окно дропается **без** траты токена (флуд не истощает бакет и
  не размножает ответы). Ключи бакетов — в памяти с TTL-эвикцией (без утечки памяти).
- **Угрозы:** блок домена api.telegram.org → остаётся Max + прочие каналы; сам
  Telegram может быть замедлен → клиент не зависит от одного мессенджера. Секретов в
  публичный канал не уходит; подпись защищает от бот-двойника.
- **Ограничения:** бот-команды требуют внешнего `SubProvider` (клиент
  subscription-сервиса) — инъектится при интеграции, в delivery захардкожена только
  форма ответа, без доменов.

### 2. DoH / DNS TXT — `internal/channel/dns`

- **Роль:** отдать sealed-указатель через TXT-записи, читаемые по обычному DNS
  (Do53) **и** DNS-over-HTTPS. Блоб → base32 → чанки ≤255 октетов; имя запроса —
  base32(key) в ≤63-октетных лейблах.
- **Скрытность:** трафик **неотличим от обычного DNS-резолва** (в этом суть, а не в
  «шифровать сильнее»). DoH дополнительно прячет сам факт запроса в HTTPS.
- **Угрозы:** DNS-подмена/poisoning → противник может вернуть **чужой** TXT, но без
  валидной подписи он отклоняется (poison-канал пропускается resolver’ом — покрыто
  тестом `TestResolverFailsOverPastPoisonedChannel`). Блок конкретного DoH-резолвера
  → другой резолвер/зона из конфига; Do53 как запасной.
- **Ограничения:** низкая ёмкость TXT; публикация TXT требует API DNS-провайдера
  (`Publisher`), иначе канал read-only (записи наполняются вне процесса). Резолвер и
  DoH-endpoint — из конфига, не хардкод.

### 3. Зеркала GitHub/GitLab raw — `internal/channel/gitraw`

- **Роль:** подписанный (и sealed для directory) блоб лежит raw-файлом в публичном
  репозитории; клиент знает набор зеркал и **ротирует** их (round-robin), пробуя
  следующее при блоке/404.
- **Угрозы:** блок одного raw-хоста / выпил репозитория → следующее зеркало
  (покрыто `TestGitRawFailsOverToNextMirror`). Подмена файла на зеркале → подпись не
  сойдётся, resolver идёт дальше. Файл публичный → внутри только sealed-указатель.
- **Ограничения:** публикация в git — внешняя операция (`RawWriter` инъектится;
  по умолчанию канал read-only, зеркала наполняются CI/оператором). Набор зеркал —
  из конфига (`DELIVERY_GITRAW_MIRRORS`), обновляемый.

### 4. Стеганография в безобидном API-трафике — `internal/channel/steg`

- **Роль:** sealed-указатель спрятан в **легально выглядящем** JSON —
  «analytics/CDP event batch» (как шлёт Segment/analytics.js). Полезные байты едут в
  полях `batch[].messageId`, которые и в реальном трафике несут непрозрачные id.
- **Threat-model / ограничения (жёстко):**
  - Стего здесь — **скрытность факта передачи**, не конфиденциальность: payload уже
    sealed+signed на уровне артефакта.
  - **Низкая ёмкость и хрупкость:** carrier, который переупаковывает/нормализует
    JSON или срезает незнакомые поля, **уничтожает** payload. Это канал **последнего
    резерва**, не основной.
  - Устойчив к **беглому** осмотру, **не** к статистическому/форматному анализу
    противником, у которого есть шаблон cover’а. Шаблон надо **ротировать**.
- **Угрозы:** обнаружение шаблона → раскрывается один канал, но не остальные и не
  сам указатель (sealed). Carrier инъектится (`Carrier`), без хардкод-хоста.

## Расширение: Snowflake-подобные волонтёрские бриджи — `internal/bridge`

Модель (реализация — заглушка-интерфейс `Broker`/`Channel`, `ErrNotImplemented`,
включается в будущей фазе без изменений в остальном коде):

- **Идея:** обычные юзеры **делятся каналом** — поднимают эфемерный rendezvous,
  который раздаёт **тот же** подписанный directory. Множество волонтёров растёт
  быстрее, чем противник успевает их перечислять (экономика асимметрии).
- **Доверие:** бридж — **недоверенная труба**. Злонамеренный волонтёр может
  дропнуть/испортить байты, но **не может** подделать directory (проверка подписи у
  клиента отклонит) и **не может** прочитать указатель (он sealed).
- **Изоляция:** бриджи эфемерны и многочисленны; per-bridge токены, без общего
  долгоживущего секрета → раскрытие одного бриджа не палит остальные (та же логика,
  что per-user REALITY short-id для нод).
- **Роль брокера:** матчит клиента с волонтёром (как Snowflake broker). Само
  rendezvous/NAT-traversal — предмет будущей фазы.

## HTTP-поверхность (`internal/httpapi`, по `openapi/delivery.yaml`)

- `GET /healthz` — liveness.
- `GET /v1/channels` — список каналов + health.
- `POST /v1/channels` — валидация дескриптора канала (живое подключение каналов —
  из конфига на старте, не из неаутентифицированного POST).
- `GET /d/{channel}/{token}` — отдать блоб, который канал держит для токена
  (base64). **Проверку подписи делает клиент**, delivery только перевозит.

## Соответствие критериям [АНТИ-БЛОК]

| Критерий | Как выполнено |
|----------|---------------|
| Нет единой точки отказа, ≥4 канала разной природы | telegram/max · doh · dns_txt · github_raw · steg + resolver-failover |
| Всё подписано, получатель обязан проверять | Ed25519, `artifact.Open` проверяет до отдачи; poison-канал пропускается |
| Snowflake-модель бриджей | описана выше, заложена интерфейсом-заглушкой `internal/bridge` |
| В открытых каналах — только зашифрованные указатели | публичные каналы несут `sealed(directory)`; секреты юзера — только по аутентиф. путям |
| Ноль хардкода доменов/IP/ключей | все эндпойнты/ключи/зеркала — из `internal/config` (env); неуказанные каналы не регистрируются |

## Тесты

- unit на каждый канал (моки внешних API): `gitraw`, `dns`, `steg`, `telegram`.
- подпись/верификация: `internal/sign`, `internal/artifact`; шифр: `internal/seal`.
- failover/registry/resolver: `internal/channel`.
- pack/unpack directory: `internal/pointer`.
- **e2e** (`internal/e2e`): артефакт, положенный через **любой** канал,
  восстанавливается и **проходит проверку подписи**; порча одного бита отклоняется
  на каждом канале; per-user subscription-артефакт round-trip.
- HTTP: `internal/httpapi`.
