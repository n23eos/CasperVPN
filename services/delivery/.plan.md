# План: delivery — избыточная многоканальная доставка подписки

Источник истины — `architecture.md` §«Децентрализованная доставка конфигов» и
`CLAUDE.md` [АНТИ-БЛОК]. Границы: работаем ТОЛЬКО в `services/delivery/`, контракты
(`packages/contracts`) заморожены — используем, не меняем.

## Проблема
Блокируют не VPN, а точку раздачи подписки. Нужна доставка одного и того же
**подписанного** артефакта через несколько разнотипных каналов; отказ любого канала
не рвёт доступ. Список каналов и точек входа — динамический, из конфига, не зашит.

## Критерии успеха (verify)
1. `go build ./services/delivery/...` — зелёно (floor Go 1.20, только stdlib+contracts).
2. `go vet ./services/delivery/...` — чисто.
3. `go test ./services/delivery/...` — unit по каждому каналу (моки внешних API),
   sign/verify, seal, + e2e: артефакт через ЛЮБОЙ канал восстанавливается и проходит
   проверку подписи.
4. ≥4 независимых канала РАЗНОЙ природы (мессенджер / DNS / git-raw / стего).
5. Всё раздаваемое подписано Ed25519; получатель обязан проверять подпись.
6. В открытые каналы уходят только **зашифрованные указатели**, без секретов юзера.
7. `docs/delivery.md` — threat-model по каждому каналу + модель Snowflake-бриджей.

## Ядро (медиа-независимое)
- `artifact` — канонический подписываемый конверт: `Kind` (directory|subscription),
  `Version`, `IssuedAt`, `Payload []byte` (непрозрачный). Детерминированная сериализация.
- `sign` — Ed25519 `Signer` + `Verifier` с keyring (`KeyID` → pubkey) для ротации ключа.
- `seal` — AES-256-GCM шифрование указателя (ключ из конфига, не хардкод).
- `pointer` — `Directory`: динамический список точек входа/зеркал/бот-хэндлов.
  В публичные каналы кладём **sealed(pointer)**, не сам per-user secret.

## Каналы (общий интерфейс `channel.Channel`: Publish/Fetch/Healthy)
1. **telegram** — бот + Max-совместимый адаптер (`BotAPI` iface, 2 реализации).
   Команда → выдаёт subscription-ссылку/deep-link Happ. Token-bucket rate-limit + антиспам.
2. **dns** — `doh` (DNS-over-HTTPS, HTTP-клиент мокается) и `dns_txt` (resolver iface).
   Блоб → base32-чанки в TXT-записях; запрос неотличим от обычного DNS.
3. **gitraw** — github/gitlab raw зеркала, ротация набора зеркал, обход по очереди.
4. **steg** — указатель, спрятанный в безобидно выглядящем JSON-ответе API (cover-carrier).
   Threat-model и ограничения — в docs.
- `channel.Registry` + `Resolver`: клиент пробует каналы по приоритету до первого
  блоба, который **проходит проверку подписи** (failover, аналог billing `payment.Registry`).

## Расширение
- `bridge` — интерфейс волонтёрских Snowflake-подобных бриджей (заглушка + docs-модель).

## HTTP API (openapi/delivery.yaml, заморожен — реализуем сигнатуры)
`/healthz`, `GET/POST /v1/channels`, `GET /d/{channel}/{token}` (format=base64|singbox|clash).
