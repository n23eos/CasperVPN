# План: services/billing — крипта-опорный биллинг CasperVPN

> Границы: работаю ТОЛЬКО в `services/billing/`. Contracts заморожены (не трогаю).
> Данные о планах/юзерах — у control-plane по API. Только stdlib (билд оффлайн,
> без внешнего реестра). Postgres — задокументированный шов, не зависимость MVP.

## Цель (критерии приёмки из задачи)

1. Приём крипты в нескольких валютах через self-hosted шлюз (BTCPay-класс) ИЛИ
   прямую ончейн-проверку. Провайдер за интерфейсом. Несколько путей одновременно;
   отказ одного шлюза не останавливает продажи.
2. Вебхуки/поллинг подтверждений → активация плана через control-plane API →
   выпуск/продление sub_token. Идемпотентность платежей.
3. Планы, сроки, грейс, автоистечение. Минимум PII: привязка по анонимному id,
   не email/телефон.
4. Антифрод-минимум: двойное зачисление, replay вебхука.
- Никаких карт/KYC. Биллинг физически отделён (свой модуль/БД, связь с
  control-plane только по HTTP за интерфейсом).

## Потоки

**1. Создание инвойса.** Канал (TG-бот) → `POST /v1/invoices {anon_user_id, plan,
provider, currency}` → billing просит шлюз создать инвойс → отдаёт адрес/сумму +
invoice_id. `anon_user_id` — непрозрачный, без PII.

**2. Подтверждение оплаты.** Вебхук `POST /v1/webhooks/{provider}` (HMAC-проверка)
ИЛИ поллер → нормализация в `PaymentEvent{provider, external_id, invoice_id,
status, amount, confirmations}` → идемпотентная обработка → при `settled`:
вычислить новый срок → вызвать control-plane для активации/продления подписки →
пометить инвойс оплаченным.

**3. Идемпотентность.** Дедуп по `(provider, external_id)` в store; инвойс —
конечный автомат (settled-once); активация привязана к payment id. Двойной вебхук →
один период.

## Математика срока / грейс / истечение

- Продление: `newExpiry = max(now, currentExpiry) + plan.Duration`.
- Грейс: после `ExpiresAt` статус `past_due` на `graceDuration`, затем `expired`.
- Sweeper: периодически переводит `active→past_due→expired`; статусы из frozen enums
  (`SubscriptionStatus`).

## Антифрод-минимум

- HMAC-подпись вебхука (btcpay); неверная подпись → 401, ничего не пишем.
- Replay: idempotency-store по `(provider, external_id)` + timestamp-окно.
- Двойное зачисление: гарантия settled-once на инвойсе/платеже.
- Недоплата: `amount >= expected` иначе не активируем.

## Контрактный пробел (единственная кросс-командная координация)

Frozen control-plane OpenAPI: есть `POST /v1/subscriptions` (create, отдаёт token=
sub_token) и `GET`, но НЕТ продления/активации срока. Нужен **аддитивный** (обратно
совместимый, по правилам заморозки через ревью) `PATCH /v1/subscriptions/{id}`
(status, expires_at). Замороженный yaml сам не редактирую — фиксирую требование в
`docs/billing.md`. `ControlPlaneClient` в billing абстрагирует это; HTTP-адаптер
готов к endpoint, тесты идут через фейк.

## Тесты

- **unit**: activator activate/renew/идемпотентность; expiry/grace переходы;
  plan catalog; проверка HMAC-подписи вебхука; store дедуп.
- **integration**: mock-шлюз end-to-end: invoice → webhook → фейк control-plane
  получает активацию; **двойной вебхук → один период** (ключевая проверка).
- Всё на stdlib `testing`, оффлайн, `make test` зелёный.

## Анти-блок соответствие

- Много платёжных путей (btcpay + onchain + mock), отказ одного ≠ стоп.
- Ноль карт/KYC, привязка по анонимному id, минимум PII.
- Billing отделён: свой модуль, свой store, control-plane только по HTTP.
- Ноль хардкода: адреса шлюзов/ключи/цены — из env/конфига, не в коде.

## Прод-гэпы (осознанно вне MVP, отмечу в docs)

Postgres+транзакции (сейчас in-memory), rate-limit, alerting, graceful shutdown,
таймауты исходящих HTTP (частично сделаю), реальный ончейн-RPC.
