# CasperVPN — набор промптов для Claude Code (параллельные агенты)

> Дата: 2026-07-07. Модель сервиса: **централизованный VPN с подпиской**. Ядро: **sing-box**.
> Клиенты: **готовые приложения (Happ и sing-box-совместимые) через subscription-ссылку** — свои нативные приложения не пишем на старте.
> Главный сквозной приоритет всех задач: **устойчивость к блокировкам со стороны государственных служб (ТСПУ/РКН-класс DPI)**.
>
> Контекст и обоснование архитектуры — в `architecture.md`. Этот файл — рабочий план: как раздать проект параллельным агентам Claude Code так, чтобы они не мешали друг другу.

---

## 0. Как это запускать

Проект разбит на **волны**. Внутри волны задачи параллельны, между волнами — зависимости. Порядок:

```
Волна 0  (1 агент, последовательно)   → фундамент, контракты, монорепо
   ↓
Волна 1  (6 агентов, параллельно)     → A B C D E F  — независимые подсистемы
   ↓
Волна 2  (2–3 агента, параллельно)    → интеграция, адаптивное переключение, админка
   ↓
Волна 3  (2 агента, параллельно)      → харденинг, симуляция блокировок, аудит
```

### Механика параллелизма

Каждый агент Волны 1+ работает в **отдельном git worktree** — это исключает конфликты и даёт честную параллельность:

```bash
# из корня репо, после Волны 0
git worktree add ../casper-node    -b agent/node
git worktree add ../casper-control -b agent/control-plane
git worktree add ../casper-sub     -b agent/subscription
git worktree add ../casper-deliver -b agent/delivery
git worktree add ../casper-billing -b agent/billing
git worktree add ../casper-telem   -b agent/telemetry
```

В каждом worktree запускаешь отдельную сессию Claude Code с соответствующим промптом ниже. Внутри одной сессии агент может дополнительно распараллеливать подзадачи через субагентов (Task tool) — где это указано.

**Правило слияния:** каждый агент трогает только свою папку (см. карту владения ниже) и общие типы — только через `packages/contracts`, который заморожен после Волны 0. Мержим по завершении волны, затем стартует следующая.

### Карта владения (кто какие папки трогает)

```
packages/contracts/     — Волна 0 (после — read-only для всех)
infra/                  — Агент A (node provisioning)
services/control-plane/ — Агент B
services/subscription/  — Агент C
services/delivery/      — Агент D
services/billing/       — Агент E
services/telemetry/     — Агент F
services/orchestrator/  — Волна 2
web/admin/              — Волна 2
test/chaos/             — Волна 3
docs/                   — все (только добавляют свои файлы)
```

### Легенда сквозных требований

В каждом промпте есть блок **[АНТИ-БЛОК]** — требования по устойчивости к блокировкам, которые агент обязан выполнить. Это не опция, это критерий приёмки.

## 1. Общие контракты (заморозить в Волне 0)

Чтобы 6 агентов не передрались за форматы данных, Волна 0 фиксирует контракты. Все остальные агенты импортируют их и не меняют. Ключевые сущности:

- **Node** — точка входа: `id`, `region`, `cloud`, `entry_ip` (эфемерный), `transports[]`, `status`, `health`, `created_at`, `rotate_after`.
- **Transport** — один способ подключения: `type` (`vless-reality` | `amneziawg` | `hysteria2` | `shadowsocks-2022`), `params` (тип-специфичные), `mimic_domain` (для REALITY).
- **User** — `id`, `sub_token` (секрет подписки), `plan`, `reality_short_id` (персональный), `status`, `expires_at`.
- **Subscription** — что отдаём клиенту: набор `Node×Transport`, отфильтрованный под юзера и его платформу/клиент.
- **HealthEvent / FieldSignal** — сигнал из поля: `node_id`, `transport_type`, `region`, `metric` (rtt/loss/reset/probe), `verdict` (`ok`|`degraded`|`blocked`), `ts`.

Полные схемы (JSON Schema + типы Go) генерит Волна 0.

## ВОЛНА 0 — Фундамент (1 агент, последовательно)

### Промпт 0 — Bootstrap монорепо и контрактов

```
Ты — старший инженер, закладываешь фундамент проекта CasperVPN: централизованного
VPN-сервиса с подпиской, устойчивого к государственным DPI-блокировкам (класс ТСПУ/РКН).
Прочитай architecture.md в корне репозитория — это источник истины по архитектуре.
Клиенты берём готовые (Happ и sing-box-совместимые) через subscription-ссылку, свои
приложения не пишем. Ядро на всех нодах — sing-box.

ЗАДАЧА: заложить структуру монорепо и ЗАМОРОЗИТЬ межсервисные контракты, чтобы дальше
6 агентов могли строить подсистемы параллельно, не конфликтуя.

Сделай:
1. Структуру монорепо (Go workspaces + отдельные сервисы):
     packages/contracts/   infra/   services/{control-plane,subscription,delivery,billing,telemetry,orchestrator}/
     web/admin/   test/chaos/   docs/
   Добавь go.work, Makefile (targets: build, test, lint, up, down), docker-compose.dev.yml
   (postgres + сервисы), .editorconfig, golangci-lint конфиг.

2. packages/contracts/ — единый источник типов. Определи как JSON Schema И как Go-типы
   (пакет contracts): Node, Transport (с вариантами vless-reality/amneziawg/hysteria2/
   shadowsocks-2022), User, Subscription, HealthEvent/FieldSignal, а также enum'ы статусов
   и версий транспортов. Опиши формат subscription-выдачи, совместимый с Happ и sing-box
   (base64-список + sing-box JSON + Clash-Meta YAML как три представления одного набора).
   Задокументируй ВСЕ поля в docs/contracts.md. После этой волны файл заморожен.

3. Внутренние API-контракты между сервисами — как OpenAPI 3.1 в packages/contracts/openapi/:
     control-plane API, subscription API, delivery API, telemetry ingest API.
   Только сигнатуры (пути, запросы/ответы, коды), без реализации. Это интерфейсы,
   по которым агенты пишут независимо.

4. docs/decisions/ — короткие ADR по ключевым развилкам, УЖЕ решённым:
   ADR-001 модель = централизованный сервис с подпиской; ADR-002 ядро = sing-box;
   ADR-003 клиенты = внешние (Happ) через subscription; ADR-004 биллинг = крипта.

5. CLAUDE.md в корне: как собирать, тестировать, границы владения папками (карта из плана),
   правило «contracts заморожены», требование [АНТИ-БЛОК] к каждому сервису (см. ниже).

[АНТИ-БЛОК] Прошей в контракты то, что делает систему живучей:
- Transport должен допускать несколько независимых типов одновременно (не монокультура).
- В Node заложи поля для быстрой ротации (rotate_after, ephemeral entry_ip) и разделения
  entry/exit (entry_node_id ≠ exit).
- В User заложи персональный reality_short_id и персональный ключ — блок одного юзера
  не должен палить остальных.
- В FieldSignal заложи всё, что нужно петле обратной связи «где что заблокировали».
Не хардкодь ни одного домена мимикрии и ни одного IP — только конфигом/из БД.

Итог: компилящийся скелет, замороженные контракты, docs/contracts.md, CLAUDE.md.
Тестов бизнес-логики пока нет — только заглушки, проходящие сборку.
```

## ВОЛНА 1 — Параллельные подсистемы (6 агентов)

> Все шестеро стартуют одновременно, каждый в своём worktree. Импортируют `packages/contracts`, не меняют его. Общаются только через контракты из Волны 0.

### Агент A — Промпт 1A — Node provisioning (инфраструктура и мимикрия)

```
Ты строишь слой инфраструктуры CasperVPN — то, что поднимает и ротирует ноды.
Читай architecture.md и packages/contracts (заморожены). Работаешь ТОЛЬКО в infra/.
Ядро ноды — sing-box.

ЗАДАЧА: «нода за минуты», одноразовая, с мимикрией под легальный HTTPS.

Сделай:
1. Terraform-модули под МУЛЬТИ-ОБЛАКО (минимум 3 провайдера, и НЕ только известные
   VPN-хостеры, чьи IP-пулы выгружают пачками): параметризуемый модуль «entry-node»
   и «exit-node» раздельно. Провайдеры — переменными, лёгкое добавление нового.
2. Ansible-плейбуки: установка sing-box, генерация конфигов из шаблонов под транспорты
   vless-reality / amneziawg / hysteria2 / shadowsocks-2022, systemd, автозапуск,
   базовый firewall, отдача метрик здоровья в формате FieldSignal на telemetry ingest.
3. REALITY-фронт: шаблон, где sing-box «крадёт» TLS-хендшейк реального крупного сайта
   (домен мимикрии — ПАРАМЕТР, список кандидатов в docs, не хардкод). Поддержка
   персональных short-id на юзера (как в contracts).
4. Скрипты ротации: поднять эфемерную entry-точку, переkey-ить REALITY, вывести старый IP,
   обновить запись Node в control-plane через его API. Цель — регенерация дешевле обнаружения.
5. Makefile/скрипты: `make node-up REGION=.. CLOUD=..`, `make node-rotate NODE=..`,
   `make node-down NODE=..`. Идемпотентно.

[АНТИ-БЛОК] — критерии приёмки:
- Entry и exit РАЗДЕЛЕНЫ: компрометация entry не раскрывает exit.
- Ни один домен мимикрии / IP не захардкожен — всё переменные.
- Нода поднимается < 5 минут «с нуля» и ротируется одной командой.
- sing-box сконфигурен так, чтобы трафик выглядел как настоящий HTTPS/HTTP-3 к чужому
  сайту (REALITY), а не как «энтропийный шум»; проверь, что нет своего TLS-серта и
  своего fingerprint. AmneziaWG-профиль ломает сигнатурный/энтропийный детект WG.
- UDP/443 может быть зарезан — у hysteria2 обязателен fallback на TCP.

Тесты: terraform validate/plan в CI (без реального apply), ansible --syntax-check,
+ molecule-сценарий поднятия ноды в контейнере и проверки, что sing-box слушает и
отдаёт валидный REALITY-хендшейк. Задокументируй в docs/infra.md.
Наружу для control-plane отдаёшь: как зарегистрировать/ротировать ноду (по openapi).
```

```

packages/contracts (заморожены). Работаешь ТОЛЬКО в services/control-plane/. Go + Postgres.
Реализуй OpenAPI из packages/contracts/openapi/control-plane.

ЗАДАЧА: хранить и управлять Node/User/Transport/Subscription, выдавать данные другим
сервисам, обеспечивать быструю подмену конфигов при блокировке.

Сделай:
1. Postgres-схему и миграции под сущности из contracts. Персональные reality_short_id и

2. Go-сервис (чистая архитектура: domain / usecase / adapters). Эндпоинты по OpenAPI:

   формирование актуального набора Node×Transport для юзера (без рендера самой подписки —

- Персональная изоляция: выдача одного юзера не раскрывает ключи/short-id других.
- Пометка ноды blocked поступает из поля (FieldSignal) и триггерит ротацию/замену.
- Никаких карт/платёжных данных в этом сервисе (биллинг отдельно, Агент E).

Тесты: unit на usecase, интеграционные на Postgres (testcontainers), контрактные тесты
против OpenAPI. docs/control-plane.md. Для Агентов C/E/F ты — источник данных по API.
```

### Агент C — Промпт 1C — Subscription service (выдача конфигов для Happ)

```
Ты строишь сервис подписки CasperVPN — то, что отдаёт клиенту рабочие конфиги. Читай
architecture.md и packages/contracts (заморожены). Работаешь ТОЛЬКО в services/subscription/.
Клиенты — ВНЕШНИЕ: Happ и любые sing-box/Clash-совместимые. Свои приложения НЕ пишем.

ЗАДАЧА: по subscription-ссылке отдавать актуальный, персональный, много-транспортный
набор точек входа в форматах, которые понимают эти клиенты.

Сделай:
1. Эндпоинт подписки `GET /sub/{token}` (по OpenAPI). Берёт набор Node×Transport у
   control-plane, рендерит в ТРИ представления одного набора (клиент выбирает по заголовку/
   параметру): (а) base64-список URI (vless://, hysteria2://, ss://) — универсально для Happ;
   (б) sing-box JSON (outbounds + правила); (в) Clash-Meta YAML. Форматы — по docs/contracts.md.
2. Happ-специфика: поддержи deep-link `happ://add/<base64sub>` и заголовки, которые Happ
   шлёт (user-agent, profile-update-interval, поддержка announce/routing если применимо).
   Проверь по актуальной документации Happ формат подписки и заголовки обновления.
3. Персонализация: подставляй персональный reality_short_id/ключ юзера; фильтруй набор по
   плану и по региону/платформе; исключай ноды, помеченные blocked.
4. Кеш выдачи с инвалидацией по сигналу из control-plane (нода blocked → пересобрать).
   Заголовок profile-update-interval, чтобы клиент сам регулярно тянул свежий список.
5. Роутинг-правила в конфиге: RU-домены/сервисы — мимо туннеля (split-tunnel), остальное —

[АНТИ-БЛОК] — критерии приёмки:
- В одной подписке ВСЕГДА несколько независимых транспортов (reality + amneziawg +

- Сам URL подписки — чувствительное место: заложи, что он приходит через delivery-каналы
  (Агент D), а не как один статический сайт. Не привязывай выдачу к единственному домену.
- Регулярное авто-обновление профиля у клиента (interval) — чтобы заблокированные ноды
  быстро вымывались из клиента.
- Ни одного захардкоженного домена/IP — всё из control-plane.

Тесты: golden-тесты рендера всех трёх форматов (сравнение с эталоном, валидными для
sing-box и Happ), проверка, что sing-box реально парсит выданный JSON (запусти sing-box
check в CI), fuzz на токенах. docs/subscription.md с примерами ссылок под Happ.
```

### Агент D — Промпт 1D — Delivery (децентрализованная раздача подписок/списка нод)

```
Ты строишь слой доставки CasperVPN — как subscription-ссылка и список нод доходят до
юзера, когда сайт-подписку блокируют. Это ЧАСТОЕ слабое звено: блокируют не VPN, а точку
раздачи. Читай architecture.md и packages/contracts. Работаешь ТОЛЬКО в services/delivery/.

ЗАДАЧА: избыточная, много-канальная, децентрализованная доставка subscription и динамич.
списка точек входа. Ни одного единственного канала.

Сделай минимум 4 независимых канала выдачи одного и того же (подписанного) артефакта:
1. Telegram-бот (и совместимый Max-бот): по команде выдаёт актуальную subscription-ссылку/
   deep-link Happ. Rate-limit, антиспам.
2. DoH / DNS TXT: отдача зашифрованного указателя на актуальную точку через DNS-over-HTTPS
   и TXT-записи (запросы неотличимы от обычного DNS).
3. Зеркала GitHub/GitLab raw (и аналоги): подписанный, зашифрованный список нод в raw-файле,
   ротация зеркал. Клиент/бот знает набор зеркал, пробует по очереди.
4. Стеганография в безобидном API-трафике: указатель на актуальную точку, спрятанный в
   легально выглядящем запросе (опиши threat-model и ограничения в docs).
Плюс: подписывай артефакты (Ed25519), клиент/бот проверяет подпись — защита от подмены.
Список каналов и точек — ДИНАМИЧЕСКИЙ, обновляемый, не зашитый.

[АНТИ-БЛОК] — критерии приёмки:
- Нет единой точки отказа в доставке: минимум 4 разнотипных канала, отказ любого не рвёт
  доступ. Каналы разной природы (мессенджер / DNS / git-raw / стего), а не 4 сайта.
- Всё, что раздаётся, криптографически подписано; получатель обязан проверять подпись.
- Опиши в docs модель Snowflake-подобных волонтёрских бриджей как канал расширения (юзеры
  делятся каналом) — реализацию заложи как интерфейс-заглушку для будущего.
- Никаких секретов юзеров в открытых каналах — только зашифрованные указатели.

Тесты: unit на каждый канал (моки внешних API), проверка подпись/верификация, e2e:
«артефакт, положенный через любой канал, восстанавливается и проходит проверку подписи».
docs/delivery.md с threat-model по каждому каналу.
```

### Агент E — Промпт 1E — Billing (крипто-подписки)

```
Ты строишь биллинг CasperVPN. Модель — подписка, оплата КРИПТОЙ (нет карт → нет точки
давления на платёжного провайдера). Читай architecture.md и packages/contracts. Работаешь
ТОЛЬКО в services/billing/. Данные о планах/юзерах берёшь у control-plane по API.

ЗАДАЧА: принимать крипто-оплату, активировать/продлевать подписку, не создавая юридической
и инфраструктурной точки давления.

Сделай:
1. Приём оплаты в нескольких криптовалютах через самостоятельно-хостируемый шлюз
   (например BTCPay-класс) ИЛИ прямую проверку ончейн — без завязки на один кастодиальный
   сервис, который могут прикрыть. Абстрагируй провайдера за интерфейс.
2. Вебхуки/поллинг подтверждений → активация плана у юзера через control-plane API →

3. Планы, сроки, грейс-период, автоистечение. Никаких персональных данных сверх минимума;
   привязка к аккаунту — по анонимному идентификатору, не по email/телефону.

[АНТИ-БЛОК] / антихрупкость — критерии приёмки:
- Несколько платёжных путей/валют; отказ одного шлюза не останавливает продажи.

Тесты: unit на активацию/продление/идемпотентность, интеграционный с тестовым крипто-

### Агент F — Промпт 1F — Telemetry (петля обратной связи «где что заблокировали»)

```
Ты строишь телеметрию CasperVPN — петлю обратной связи, которая превращает каждую
блокировку в обучающий сигнал. Читай architecture.md и packages/contracts. Работаешь
ТОЛЬКО в services/telemetry/. Формат сигнала — FieldSignal из contracts.

ЗАДАЧА: собирать АНОНИМНЫЕ сигналы из поля (rtt/loss/reset/пробинг/verdict по региону и

транспорты автоматически.

Сделай:
1. Ingest API (по OpenAPI) для приёма FieldSignal от нод (Агент A) и, опционально, от

   регион+транспорт+метрика+вердикт. Rate-limit, защита от отравления данных (poisoning).

[АНТИ-БЛОК] — критерии приёмки:

Тесты: unit на агрегацию/детекторы, симуляция «регион заблокировал reality» → корректный
агрегат, тест на poisoning-устойчивость. docs/telemetry.md.
```

## Сквозной чек-лист устойчивости к блокировкам (проверять на каждом мерже)

1. Мимикрия, а не «шифрование посильнее»: трафик выглядит как настоящий HTTPS/HTTP-3 (REALITY), WG обфусцирован (AmneziaWG), UDP-фоллбэк на TCP есть.
2. Разнообразие, а не монокультура: в каждой подписке ≥3 независимых транспорта; оркестратор не схлопывает выбор.
3. Нет единой точки отказа в доставке конфигов: ≥4 разнотипных канала, всё подписано.
4. Персональная изоляция: свой short-id/ключ у юзера — блок одного не палит остальных.
5. Разделение entry/exit + быстрая одноразовая ротация нод (регенерация дешевле обнаружения).
6. Петля обратной связи: каждая блокировка из поля → автоматическая ротация/переключение.
7. Ноль хардкода доменов/IP; ноль карт и лишнего PII (нет рычагов давления).
